# Offline-signed transactions get their expiry by proposal retarget rather than a builder override

A transaction calculated by an Indexerless wallet inherits its expiry from the stored proposal's target height (the wallet's possibly stale chain view plus forty blocks), so it could expire before an Indexer was ever available to transmit it (issue #2455). We decided that `calculate_stored_proposal`, when the client is Indexerless, rebuilds the stored proposal through the public `Proposal::multi_step` constructor with its target height lifted to the last height of the consensus-branch epoch the wallet believes it is in: one below the next scheduled network-upgrade activation or, when none is scheduled, the highest target whose expiry ZIP 203 can encode as a height (below 500,000,000). The steps and their anchors are untouched, the stored target is never lowered, and an Indexer-connected calculation keeps the ordinary forty-block expiry, since connected callers are expected to transmit promptly.

The epoch boundary is the true limit rather than a compromise. Every Zcash signature commits to a consensus branch ID selected by the target height, so no pre-signed transaction survives a network upgrade regardless of its `nExpiryHeight`. "Valid until the next scheduled upgrade" is the longest life any mechanism could deliver, and the retarget delivers exactly that using only public `zcash_client_backend` API.

## Considered Options

Building with the literal ZIP 203 no-expiry sentinel (`nExpiryHeight = 0`) shipped first and was reverted: `Builder::new` computes expiry internally and exposes no seam, so the sentinel required pinning ten crates to a librustzcash fork, which the no-new-dependencies/no-patches rule forbids, and the sentinel's practical lifetime was no longer than the retarget's, since the branch-ID commitment bounds both at the next upgrade. It also forced a special case into pepper-sync's expiry check, which the retarget removes entirely. The PCZT route (`create_pczt_from_proposal`) is librustzcash's sanctioned offline-signing shape but would add the `pczt` dependency and new machinery. It remains the eventual convergence point with Ironwood PCZT signing (issue #2425). Review rejected retargeting unconditionally (also when connected): a connected `calculate` keeps the standard expiry, so the long-lived artifact is exclusively an offline product. We rejected a safety margin below the activation boundary because the branch-ID commitment already makes the boundary absolute.

## Consequences

The `Calculated` status embeds the lifted target height rather than a near-tip height, and ordering and display treat it as opaque. A transaction calculated online and left untransmitted past forty blocks still expires, by design. One property remains to confirm end-to-end when a connected harness exercises the flow: zebra's mempool imposes no maximum-expiry-distance rule below the ZIP 203 threshold. Code review of the release notes found none, and a libtonode round-trip is the definitive check.
