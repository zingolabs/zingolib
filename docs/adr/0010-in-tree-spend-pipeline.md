# zingolib owns its spend pipeline; zcash_client_backend leaves the dependency tree

Zingo needs a data-carrier output (OP_RETURN) on the final transaction of a send — the memo channel for THORChain/MAYAChain swap deposits — and `zcash_client_backend`'s released Proposal API has no seam for one: the upstream attempt to add it (librustzcash PR #2441) was closed unmerged, and the no-new-dependencies/no-patches rule (see ADR 0008's history) forbids pinning the zingolabs fork that carries it. An audit found that zcb's real footprint in zingolib is exactly three orchestration entry points — `propose_transfer`, `propose_shielding`, and `create_proposed_transactions` — fed by a trait-impl file (1,095 lines in the ironwood era) in which 49 of 69 trait methods are `unimplemented!()` stubs, plus incidental type imports that are re-exports of crates zingolib already depends on directly. We decided to reimplement that orchestration as a module inside zingolib and remove `zcash_client_backend` from zingolib's manifest entirely: `zip321` becomes a direct dependency (zcb re-exports it verbatim), the four zcb trait impls are deleted rather than re-abstracted, and the in-house proposal type carries the data-output field natively. Everything consensus-critical stays upstream — ZIP-317 fee arithmetic (`zcash_primitives::transaction::fees::zip317::FeeRule`), the transaction `Builder` including `add_transparent_null_data_output` (already published in the pinned releases), proving, keys, and addresses. The module owns orchestration only: which notes to select, what change to make, which outputs each step gets.

The module is layered functionally, effects only at the edges. A pure plan layer maps a read-only wallet view and a payment request to a proposal — selection, change, ZIP-317 fee sizing (feeding the upstream `FeeRule` the serialized size of every output it will emit, the null-data output included), ZIP-320 TEX step-splitting, and refund-address *derivation*. A wallet-pure build layer maps a proposal, keys, provers, and pre-extracted witnesses to signed transactions; it never touches the wallet, and its internal randomness (proofs, signature nonces) is accepted — the purity criterion is freedom from wallet-state effects, not bitwise determinism. A single apply site performs the mutations: reserving the derived refund addresses, recording the calculated transactions, marking the wallet dirty. The ADR 0006 proposal slot and the facade's sync-pausing are deliberately untouched: what ADR 0006 withdrew was moving protocol state to the shells, not purifying the machinery beneath it, and this design does the latter without relitigating the former. Errors follow the typed regime established by PR #2464 (issue #2446): one error enum per layer, composing into the existing client error chain, JSON rendering only in the shells.

## Considered Options

Pinning the `zingolabs/librustzcash` fork branch that adds proposal-level OP_RETURN was rejected outright by the standing no-forks rule — the same rule that killed the expiry-sentinel fork pin recorded in ADR 0008. Waiting for upstream to land the feature leaves the product need unmet on an unbounded timeline and keeps the stub-heavy trait ballast either way. Keeping zcb as a types-only dependency while moving the functions in-house was rejected because the version-bump treadmill and the public-API leakage remain, and the upstream `Proposal` type — the very thing that cannot carry OP_RETURN — would still dictate the wallet's proposal shape. A separate workspace crate for the pipeline was rejected because it cannot depend on zingolib (`LightWallet` lives there), so it would need its own wallet-abstraction traits — recreating the indirection this decision deletes; an in-tree module reads wallet state directly. pepper-sync's serialization-only zcb dependency is a separately published crate with its own dependency policy and is explicitly out of scope.

## Consequences

Zingolib takes ownership of roughly 1.5–2.5k lines of consensus-adjacent orchestration: greedy input selection (whose core loop zingolib's `select_spendable_notes` already implements), single-output change with dust policy, the ZIP-320 TEX two-step flow, and correct ZIP-317 logical-action counting — including the null-data output, which the change computation must count even though the arithmetic itself stays upstream. Upstream improvements to that orchestration no longer arrive for free and must be ported deliberately. The migration needs behavioral-equivalence coverage (the synthetic-wallet proposal tests are the base). `zcash_client_backend::serialization::shardtree::read_shard`, used for legacy wallet-file reading, needs a new home. ADR 0008's retarget mechanism simplifies from reconstruct-via-`Proposal::multi_step` to updating a field on a type we own. The `lightwalletd-tonic` zcb feature was found vestigial during the audit and disappears with the dependency. Reserving refund addresses at apply time rather than at propose time is a deliberate semantic divergence from `zcash_client_backend`: today an abandoned TEX proposal burns ephemeral address indexes and erodes the gap limit; under this design an address is reserved exactly when a transaction bearing it comes into existence, so abandoned proposals leave no trace. During the migration the old zcb path and the new pipeline coexist so behavioral-equivalence tests can compare their proposals; that scaffolding, and the zcb dependency with it, is deleted at cutover, after which the per-layer table tests carry the guarantees.
