# Library Birthday: a release-stamped floor for never-online wallet creation

Creating a `NewSeed` wallet requires a `chain_height` from which the Birthday is derived, but an Indexerless consumer has no chain tip to supply, and demanding one from an end user is untenable (zingo-mobile cannot ask). We decided that each zingolib release carries a per-ChainType constant (the Library Birthday) recording a block height that had already been mined when the release was cut. Because no wallet can be created by a release before that release exists, the constant is always a safe Birthday for a wallet whose seed is newly generated. Bumping the constant is a release-checklist step, and its invariant is exactly this: the recorded height must already have been mined at release time. A scheduled network-upgrade activation height does not satisfy the invariant, because activations are scheduled ahead of their heights.

The library only publishes the value (`lib_birthday(chain)`); it never substitutes it implicitly. `WalletConfig::NewSeed` keeps its mandatory `chain_height: u32`, and the caller decides what to pass: an Indexer-reported tip when online, the Library Birthday when Indexerless, or a caller-observed height when it has fresher information (zingo-cli expresses this as an optional `--birthday` override for new offline wallets). Restores are untouched: a restored seed or viewing key may predate the library, so `MnemonicPhrase`/`Ufvk`/`Usk` continue to require a caller-supplied Birthday in every mode.

## Considered Options

Making `chain_height` an `Option<u32>` with `None` meaning "use the constant" was rejected because it turns `WalletConfig::resolve` from a pure function of its fields into one that reads an ambient value, and it lets callers opt out of thinking about the height. Recording a creation wall-clock timestamp and estimating the height at first Indexer contact was rejected as more machinery for the same guarantee, with clock trust added. Setting the Birthday to the chain tip at first Indexer contact was rejected because it loses funds received between offline creation and first contact. The cold-receive case is a primary reason offline wallets exist. Falling back to Sapling activation is safe but forces a whole-chain first scan, which is the failure mode the current mandatory-birthday error exists to prevent.

## Consequences

A consumer pinning an old zingolib release creates offline wallets whose first sync scans from that release's stamp forward. Staleness costs scan time, never funds. Wallets serialize the derived Birthday permanently, so a wrongly-stamped constant (a height not yet mined at release) is the one unrecoverable failure; the release checklist is the guard.
