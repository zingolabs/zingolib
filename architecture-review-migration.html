The Orchard→Ironwood migration:
differentiating the private path from the immediate paths

Scope: the migration orchestrator lightclient/migrate.rs (3362 lines, 27 methods) and the wallet/migration/ backend. The friction is that three flows — the private Scheduled machinery, the non-private one-call Immediate, and the Drain — share one MigrationState slot and one impl block, differentiated at runtime rather than by a seam. The privacy distinction is real and consent-bearing; today it is enforced by scattered checks.

One interface. The guards collapse into “which constructor set the mode.”

Files
lightclient/migrate.rs — start_ironwood_migration :432, migrate_to_ironwood :1662, fold_in_overdue_parts :1098, reconcile Rebuild :998 · wallet/migration/schedule.rs — place / place_immediate
Problem
start and migrate_to_ironwood inline the same “hash → bind → place → PartsScheduled” critical section, differing only in which of six placement calls they reach, and the privacy rule rests on two remembered runtime mode == guards. The seam is asymmetric: plan_schedule is a batch planner for the private path, but there is no immediate counterpart, so migrate_to_ironwood hand-rolls its own place_immediate loop (:1678–1685), as does catch-up (:1090–1100).
Solution
One deep operation on MigrationState that binds and places, choosing jittered vs immediate by the stored MigrationMode. Both entry points call it; the placement monopoly in schedule.rs gains a single caller.
Wins
  • locality: the private/immediate fork behind one interface
  • leverage: one place to test consent + placement + activation floor
  • deletion test: the immediate inline section concentrates, not moves
  • six placement sites drop to one policy

  • two adapters justify the remaining faces

Files
wallet/migration/drain.rs (doc claim) · lightclient/migrate.rs — build_and_transmit :1478, build_transactions :1511, shared call sites :1457 (drain) & :1739 (split round)
Problem
The one honest coupling between the flows is a pair of private orchestrator methods, invisible as a seam and easy to widen by accident. build_transactions is in fact reached by all three flows (drain, the immediate split round, and the scheduled continue_note_splitting :624 directly), and in the backend the drain↔scheduled coupling concentrates at split.rs’s bundle/fee/output primitives — the real referent of “shares nothing but the builder.”
Solution
Lift build_and_transmit into a named shared batch-builder both the drain and the split rounds call — the single visible point of contact (pairs with candidate 02).
Wins
  • two callers justify the seam (drain, split rounds)
  • “shares only the builder” becomes checkable, not prose
  • the shared cleanup contract tested once

Top recommendation

Start with 01 — give the mode one consent-and-placement seam.

It is the heart of the ask: the private↔immediate distinction is exactly the private/non-private line you want sharpened, and today it is enforced by two remembered runtime guards plus two duplicated critical sections. Folding the fork into a single MigrationMode-owned placement operation makes the privacy rule structural instead of vigilant, and it is the smallest change with the highest leverage — one interface, one test surface for consent, binding, and the activation floor.

Pair it with 02, split by flow, which gives 01 (and 03, 04) a clean home: once each flow is its own deep module, the mode’s legality reads off the module you are in rather than a scattered check.
